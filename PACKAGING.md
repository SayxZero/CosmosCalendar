# Установочные пакеты

Как собираются пакеты «Космос календаря» для выпуска, что уже готово и что
осталось.

| Платформа | Планер | Сервер | Статус |
|---|---|---|---|
| Windows | MSI и setup.exe (WiX 3) | MSI и setup.exe (WiX 3) | **готово** |
| Android | APK, подписанный ключом выпуска | — | **готово** |
| Linux | `.deb`, AppImage | архив `.tar.gz`, Docker-образ; сайт — так же | **сервер и сайт готовы** (Docker в WSL), планера нет |

## Одна команда

Из корня зонтичного репозитория, в PowerShell:

```powershell
.\build-packages.ps1
.\build-packages.ps1 -Keystore D:\Keys\cosmos-release.jks   # другой ключ
.\build-packages.ps1 -SkipApk                               # без APK: ни ключа, ни пароля
.\build-packages.ps1 -SkipLinux                             # без Linux
.\build-linux.ps1                                           # только Linux
```

С `-SkipApk` (у батника — `-skipapk`) собирается всё, кроме APK: ключ выпуска
не проверяется, пароль не спрашивается, а `Build\Android` не очищается — APK
прошлого прогона с паролем остаётся там и попадает в `SHA256SUMS.txt`. Так
пересобирают установщики Windows, не вводя пароль каждый раз; версия APK в
его имени показывает, к какому планеру он относится.

Если файл в `Build\` занят (установщик запущен прямо оттуда; Windows
Installer держит MSI ещё несколько минут после установки), скрипт
останавливается на очистке и называет файл.

На экране — только этапы: пока этап идёт, рядом крутится индикатор и идёт
время, потом — «готово» (с числом пройденных тестов, подписью APK) или
«ошибка» со строками ошибок из журнала и путём к нему. Весь вывод сборок —
в `Build/logs/NN-<этап>.log`. Остановка на первом неудачном этапе.

```
  [ OK ] Проверка окружения                        готово · планер 1.1.0, сервер 1.3.0
  [ OK ] Ключ выпуска                              готово · cosmos-release.jks
  [ OK ] Планер: сборка и тесты              1:12  готово · тесты: пройдено 60, пропущено 1
  [ |  ] Планер: MSI и setup.exe             0:09  выполняется
```

`build-packages.bat` делает то же самое с полным выводом сборок в консоль
(`-noui` — без ожидания клавиши в конце).

Результат — в `Build/` (в `.gitignore`, каждый запуск собирает заново):

```
Build/
  Windows/  CosmosCalendar-<v>-x64.msi    CosmosCalendar-<v>-setup.exe
            CalendarServer-<v>-x64.msi    CalendarServer-<v>-setup.exe
  Android/  CosmosCalendar-<v>.apk
  Linux/    CalendarServer-<v>-ubuntu26.04-x64.tar.gz
            CalendarWebServer-<v>-linux-x64.tar.gz
            tests/ — отчёты тестов из контейнеров
  SHA256SUMS.txt
```

Скрипт по очереди зовёт сборку каждого проекта и собирает результат:

1. `Calendar\build-exe.bat` — сборка, тесты, раскладка Qt в `release\`;
2. `Calendar\build-installer.bat -skipbuild` — MSI и setup.exe из готовой
   `release\` (`build-packages.bat` зовёт его без ключа, и сборка идёт внутри);
3. `Calendar\build-apk.bat` — APK, подписанный **ключом выпуска**;
4. `CalendarServer\build-server.bat` — сборка сервера и админ-панели и оба
   набора тестов в `build-release\` (не в `build\`: оттуда мог работать
   боевой сервер, и его exe занят);
5. `CalendarServer\build-installer.bat -skipbuild` — раскладка Qt для
   сервера и панели, MSI и setup.exe;
6. `build-linux.ps1` — серверы для Linux в Docker (ниже, «Linux: Docker в
   WSL»). Нет Docker в WSL — этап пропускается с запиской в `Build\Linux`,
   пакеты Windows от него не зависят.

Версии берутся из `project(... VERSION x.y.z)` в `CMakeLists.txt` каждого
проекта. Планер и сервер выпускаются независимо: их совместимость держит
версия API, а не совпадение номеров.

Каждый проект собирает свои пакеты и сам по себе: `build-installer.bat` без
параметров кладёт их в `release\installer` (планер) или
`build-release\installer` (сервер), `-out <папка>` — куда угодно.

## Ключ выпуска Android

- Файл — `%USERPROFILE%\.android\cosmos-release.jks` (PKCS12, алиас `cosmos`);
  другой путь — переменная `COSMOS_KEYSTORE`.
- Пароль спрашивается один раз, в начале, скрытым вводом (звёздочки).
  `build-packages.ps1` вставляет его из буфера обмена по Ctrl+V и
  Shift+Insert — первой строкой, без перевода строки, если он скопирован вместе
  с ним; так же работает вставка правой кнопкой и в Windows Terminal. Пароль
  сразу проверяется `keytool`: неверный — ещё попытка (всего три), Esc —
  отмена. Сборка без вопросов — переменная `COSMOS_KEYSTORE_PASS`.
- Пароль идёт дочерним процессам только через окружение, `apksigner` берёт
  его оттуда (`env:`) — ни в одной командной строке его нет, и любые символы
  в нём безопасны. Исключение — `build-packages.bat`: его пароль проходит
  через `set`, и двойной кавычки в нём быть не должно.
- В пароле PKCS12 — только ASCII: Java не создаст и не откроет хранилище с
  кириллицей в пароле («Password is not ASCII»).
- Ни ключ, ни пароль в репозитории не попадают: `.gitignore` планера отсекает
  `*.jks` и `*.keystore`, а скрипты получают их только из окружения.
- Копия ключа и пароля — в менеджере паролей. Потерянный ключ — это конец
  обновлений поверх установленного приложения.
- Повседневные сборки (`build-release.bat`, `build-apk.bat`) по-прежнему
  подписываются **отладочным** ключом. APK с ключом выпуска не встанет поверх
  отладочного и наоборот: переход телефона на сборку выпуска — один раз,
  через резервную копию планера («Настройки → Данные»), удаление,
  установку и восстановление.

## Windows: что внутри пакетов

Исходники — `packaging/windows/` каждого проекта; нужен WiX Toolset 3 (на
машине автора 3.7; путь — `%WIX%`, либо `PLANNER_WIX` / `SERVER_WIX`).

- **MSI** собирается из папки, разложенной `windeployqt`: `heat` описывает её
  файлы целиком, поэтому пакет несёт ровно то, что нужно программе без Qt в
  `PATH`. 64-битный, для всех пользователей (Program Files, нужны права
  администратора), окна установки по-русски, без страницы лицензии.
  Страницы: приветствие → папка установки → «Ярлыки» (флажки «Добавить
  иконку на рабочий стол» и «Добавить иконку в меню «Пуск»» — у сервера
  «иконку админ-панели», оба отмечены) → готово к установке. Без окон
  (`msiexec /qn`) ставятся оба ярлыка;
  `INSTALLDESKTOPSHORTCUT=0` или `INSTALLSTARTMENUSHORTCUT=0` их отменяют,
  `INSTALLFOLDER=<папка>` задаёт папку.
- **Каждая версия — большое обновление**: старая удаляется целиком, новая
  ставится; поставить более старую поверх новой нельзя. Код обновления
  (`UpgradeCode`) у каждого пакета постоянный и не меняется никогда.
- **Планер**: ярлыки — по выбору, флажок «Запустить» в конце, ссылки
  `calendar-planner://` открывают планер (переход по ссылке общего доступа).
- **Сервер** ставится службой Windows `CosmosCalendarServer`: учётная
  запись LocalService, запуск вместе с системой и сразу после установки, после
  сбоя — перезапуск через 10 секунд (третий сбой за сутки её останавливает).
  Окна у неё нет; журнал — `server.log` в папке данных.
  - Папка данных — `%ProgramData%\CalendarPlanner\CalendarServer`:
    `server.ini` (ставится один раз и больше не перезаписывается, при удалении
    остаётся), `server.db`, `server.log`, `backups\`. Права на неё — только у
    системы, администраторов и службы: база хранит все аккаунты.
  - Правило брандмауэра — для программы сервера в частных сетях, на любой
    порт, который задаст `server.ini`.
  - Ярлыки — админ-панели (`CalendarServerAdmin.exe`), по выбору; на последней
    странице MSI — флажок «Открыть админ-панель сервера». Панель сама просит
    права администратора (UAC).
  - Рядом с панелью — бенчмарк `CalendarServerBench.exe`: его запускает
    страница «Многопоточность», и он подбирает настройки нагрузки для машины
    (тестовую базу кладёт в `benchmark\` папки данных).
  - Переход с версии 1.0, работавшей в консоли: установщик закрывает такой
    сервер, если он запущен из той же папки, ещё до проверки занятых файлов, а
    после копирования файлов сервер сам (`--import-db`) переносит в службу
    копию базы из `%APPDATA%\CalendarPlanner\CalendarServer` того, кто
    ставит, — однажды, пока у службы нет аккаунтов. Прежняя база остаётся на
    месте; что сделал перенос — в `server.log`.
  - Сервер не запустился (порт занят) — установка всё равно завершается, а
    админ-панель показывает ошибку и последние строки журнала.
- **setup.exe** — загрузчик WiX (Burn) с тем же MSI внутри. Окно своё, не
  мастер MSI: стандартная тема WiX с кнопками шире стандартных, чтобы
  поместились русские слова (`setup-theme.xml`), русские строки
  (`setup-ru.wxl` — у WiX 3.7 есть только английские) и логотип планера. В
  «Параметрах» — папка установки и те же два флажка ярлыков, отмеченные;
  загрузчик передаёт их в MSI. На последней странице у планера — «Запустить»,
  у сервера — «Админ-панель». В «Программах и компонентах» видна одна
  запись — сам setup.exe.
- **Данные не трогаются**: ни установка поверх, ни удаление не касаются
  `%APPDATA%\CalendarPlanner` планера и папки данных сервера; удаление сервера
  убирает службу и правило брандмауэра, а базу оставляет.
- **Подписи кода нет**: SmartScreen предупредит о неизвестном издателе.

## Linux: Docker в WSL

Linux-сборки серверов идут в Docker на Ubuntu 26.04 LTS, с Qt и .NET из её
репозиториев (Qt 6.10.2, .NET SDK 10.0.114; на Windows сервер собирается с
Qt 6.5.3, и тот же код проходит тесты на обеих). Docker — **Docker Engine внутри дистрибутива WSL 2**, без Docker
Desktop: открытый код, никаких соглашений, нет своей виртуальной машины и
приложения в трее, а дистрибутив тот же, что и целевая система. Из Windows
его вызывают через `wsl.exe`: `build-linux.ps1` делает это сам, руками —
`wsl -d Ubuntu-26.04 docker …`.

### Установка (один раз)

Первые три шага требуют прав администратора или создают учётную запись — их
делает владелец машины.

1. PowerShell от имени администратора — компоненты «Платформа виртуальной
   машины» и WSL и сам WSL с GitHub (≈370 МБ), затем перезагрузка:

   ```powershell
   wsl --install --no-distribution --web-download
   ```

2. После перезагрузки (`wsl --version` показывает WSL и ядро) — дистрибутив
   на диск с местом (≈420 МБ загрузки; образы и кэш Docker вырастают до
   5–8 ГБ, а виртуальный диск WSL сам не сжимается):

   ```powershell
   wsl --install -d Ubuntu-26.04 --location N:\WSL\Ubuntu-26.04 --web-download
   ```

   Первый запуск спрашивает имя и пароль пользователя Linux (пароль — только
   для `sudo` внутри) и согласие на сбор метрик (Ubuntu Insights; `n`).
3. Docker внутри — `wsl-docker-setup.sh` зонтика (`docker.io` и
   `docker-buildx` из архива Ubuntu, systemd, пользователь в группе
   `docker`), затем перезапуск дистрибутива:

   ```powershell
   wsl -d Ubuntu-26.04 -u root sh /mnt/d/Prog/Calendar/wsl-docker-setup.sh 8.8.8.8 8.8.4.4
   wsl --terminate Ubuntu-26.04
   wsl -d Ubuntu-26.04 docker version
   ```

   Адреса после имени скрипта — DNS для дистрибутива вместо посредника
   Windows на шлюзе WSL: с VPN на стороне Windows тот молчит, и имена не
   находятся ни у `apt`, ни в контейнерах (`ISSUES.md`). Без VPN их можно не
   указывать.

Другое имя дистрибутива — `-Distro` у `build-linux.ps1` или переменная
`COSMOS_WSL_DISTRO`.

### Что собирается

`build-linux.ps1` (UTF-8 с BOM, как `build-packages.ps1`, и с тем же видом
этапов) кладёт всё в `Build\Linux`, журналы — в `Build\logs\linux-*.log`:

1. **Сервер** — `CalendarServer/packaging/linux/Dockerfile`: сборка CMake и
   Ninja, тесты `tst_server`, `tst_bench`, `tst_admin` (`QT_QPA_PLATFORM=offscreen`)
   внутри сборки образа, архив `CalendarServer-<v>-ubuntu26.04-x64.tar.gz`
   (`bin/` — сервер, бенчмарк, админ-панель; `deploy/` — служба systemd и
   пример `server.ini`; `INSTALL.txt`) и образ `cosmos-calendar-server:<v>`.
2. **Сайт** — `CalendarWebServer/packaging/linux/Dockerfile` с
   `CalendarWeb/site` вторым контекстом: сборка, `dotnet test`, архив
   `CalendarWebServer-<v>-linux-x64.tar.gz` (программа, зависимая от ASP.NET
   Core Runtime 10, и `site/` рядом) и образ `cosmos-calendar-web:<v>`.
3. **Проверка образов**: сервер запускается в своей сети Docker и отвечает на
   `/api/ping` — изнутри (проверка здоровья образа) и из Windows на
   `127.0.0.1:8767`; тесты сайта прогоняются ещё раз против него, уже с тестом
   настоящего сервера (`WEB_TEST_SERVER`); образ сайта перед ним отвечает на
   `127.0.0.1:8768`. Контейнеры и сеть потом удаляются; порт 8765 боевого
   сервера не трогается.

Архив выгружается из образа только после пройденных тестов: стадия `dist`
зависит от стадии `test`. Первый прогон качает образ Ubuntu, Qt и .NET SDK
(около 450 МБ) и идёт минут пятнадцать-двадцать; дальше слои берутся из
кэша: правка исходников — полторы минуты с тестами, без правок — полминуты,
и тесты тогда обычно не перезапускаются (их слой тоже в кэше). `-NoCache`
собирает всё заново.

Тестов на Linux столько же, сколько на Windows, кроме одного: проверка
службы Windows в `tst_admin` пропускается. Итог — в строке этапа и в
`Build\Linux\tests\` (отчёты QtTest и `dotnet test`; отчёт сайта — последнего
прогона, против образа сервера).

Каждый Dockerfile годится и сам по себе, без зонтика (команды — в его
шапке). Образы для запуска:

```bash
docker network create cosmos
docker run -d --name calendar-server --network cosmos -p 8765:8765 \
    -v calendar-data:/data cosmos-calendar-server:1.3.0
docker run -d --name calendar-web --network cosmos -p 8780:8780 \
    -v calendar-web-data:/data cosmos-calendar-web:1.0.0 --upstream calendar-server:8765
```

На машине разработки так не запускать: порт, опубликованный в WSL, WSL
отдаёт на `127.0.0.1` Windows, а 8765 там занят боевой службой. Для проверок
— `-p 127.0.0.1:8767:8765` и выше, как в `build-linux.ps1`.

Сервер в образе — не root (`calendar`), база — в томе `/data`; лишние
ключи (`--no-registration`, `--trusted-proxies`) дописываются после имени
образа. Сайт — тоже не root (`web`), его папка данных (`legal.json`, файл
оферты) — том `/data` своего контейнера: `-v calendar-web-data:/data`.

## Что дальше

### Linux

Сервер и сайт собираются (выше, «Linux: Docker в WSL»). Дальше:

- планер — свой `packaging/linux/Dockerfile` на той же Ubuntu 26.04: `.deb`
  (CPack DEB, зависимости от системного Qt, явно плагины мультимедиа и
  драйвер SQLite), затем AppImage; нужны `.desktop` с обработчиком
  `calendar-planner://`, иконки hicolor и AppStream metainfo. Заглушка —
  `Calendar/packaging/linux/README.md`;
- сервер — `.deb` поверх того же Dockerfile (`/usr/bin/calendar-server`, unit
  systemd с путём через `configure_file`, `sysusers.d`, `tmpfiles.d`,
  `/etc/calendar-server/server.ini`; `remove` и `purge` базу не трогают);
- сайт — `.deb` или unit systemd рядом с сервером;
- сборка для других дистрибутивов (Debian 13, Fedora): архив сервера связан с
  Qt той системы, на которой собран.

### Остальное, по мере надобности

- **Одна версия на всё.** Сейчас у планера версия ещё продублирована в
  `QT_ANDROID_VERSION_*` (`versionCode` 1), в манифесте и в `Calendar.pro`.
  Перед вторым выпуском APK `versionCode` должен расти — выводить его из
  `PROJECT_VERSION` (`major*10000 + minor*100 + patch`).
- **Подпись кода Windows** — Azure Trusted Signing или сертификат OV/EV;
  подписываются exe внутри, MSI и setup.exe.
- **CI** — GitHub Actions в каждом репозитории: сборка и тесты на каждый push,
  пакеты по тегу `vX.Y.Z` в черновик Release; ключ выпуска — секретами.
- **Служба Windows для сервера** — обёртка WinSW.
- **Google Play** — только после перехода на Qt 6.8+ (страницы памяти 16 КБ,
  `targetSdk` по требованию Play, отступы Android 15, тип службы переднего
  плана у `AlarmService`), AAB и деклараций разрешений.
- **Flatpak / Flathub** — когда будут снимки экрана и стабильные метаданные.

### Почему без отдельного репозитория упаковки

Описание пакета — свойство проекта: что ставить и куда, ярлыки, ассоциации,
зависимости. В отдельном репозитории оно отставало бы от кода. Поэтому
исходники пакетов лежат в `packaging/` каждого проекта, а зонтик только
запускает их сборку разом. Свой репозиторий понадобится, когда его потребует
канал распространения (Flathub, свой APT) или появится общая инфраструктура CI.

## Проверка выпуска

- **Windows** — на чистой машине без Qt: установка, запуск, создание записи;
  установка следующей версии поверх (данные на месте, одна запись в
  «Программах»); удаление (`%APPDATA%\CalendarPlanner` остаётся); переход по
  ссылке `calendar-planner://share?…` из браузера.
- **Android** — APK с ключом выпуска на чистый эмулятор и обновление поверх; на
  телефоне с настоящими данными — только через резервную копию.
- **Сервер** — установка поверх 1.0 при запущенном консольном сервере:
  консольный закрыт, служба работает, аккаунты на месте, «Проверить сервер»
  из планера отвечает, обмен идёт. Админ-панель из «Пуска»: вопрос UAC,
  страницы «Сервер» (работает, адреса), «Пользователи», «Аналитика», копия и
