# Космос календарь — устройство системы

Документ описывает систему целиком: из каких частей она состоит, как планер и
сервер говорят друг с другом, где какие данные и как части развёртываются и
совмещаются по версиям. Внутреннее устройство каждой части — в её собственном
документе:

- планер — [`Calendar/DesDoc.md`](Calendar/DesDoc.md)
  ([SayxZero/Calendar](https://github.com/SayxZero/Calendar));
- сервер — [`CalendarServer/DesDoc.md`](CalendarServer/DesDoc.md)
  ([SayxZero/CalendarServer](https://github.com/SayxZero/CalendarServer)).

Здесь их устройство не повторяется — только то, что на стыке.

## 1. Состав

```
   ┌──────────────── устройства пользователя ─────────────────┐
   │                                                          │
   │  Планер на компьютере        Планер на телефоне          │
   │  (Windows, Linux)            (Android 6+)                │
   │  SQLite: planner.db,         SQLite: planner.db,         │
   │  accounts/<ключ>.db          accounts/<ключ>.db          │
   │                                                          │
   └───────────────┬──────────────────────────┬───────────────┘
                   │  HTTP/1.1 + JSON         │
                   │  (только у аккаунтов)    │
                   ▼                          ▼
            ┌──────────────────────────────────────┐
            │  CalendarServer (Windows, Linux)     │
            │  SQLite: server.db                   │
            │  аккаунты, ключи сеансов, записи,    │
            │  общие календари и ссылки            │
            └──────────────────────────────────────┘
```

| Часть | Что делает | Платформы | Зависимости |
|---|---|---|---|
| **Планер** (`Calendar/`) | календарь, задачи, привычки, напоминания и будильник; интерфейс, хранение, импорт и экспорт | Windows, Linux, Android | Qt 6.4+: Widgets, Sql, Network, Multimedia (кроме Android) |
| **Сервер** (`CalendarServer/`) | аккаунты, обмен записями между устройствами, общие календари | Windows, Linux (служба systemd) | Qt 6.2+: Core, Network, Sql |

Обе части — Qt 6 / C++17, без сторонних библиотек, каждая собирается CMake и
qmake. Код у них общий только по смыслу: сервер не подключает исходников
планера и наоборот, их связывает один протокол.

**Планер главный.** Без аккаунта он сети не касается вовсе и работает с
локальной базой. Аккаунт — это ещё один файл базы на устройстве и фоновая
служба, которая держит его в согласии с сервером; интерфейс работает с базой
одинаково в обоих случаях. Сервер поэтому необязателен, и его недоступность
не мешает работе: правки копятся в журнале устройства и уходят, когда связь
вернётся.

## 3. Протокол

### 3.1 Транспорт

HTTP/1.1 с постоянными соединениями, тела запросов и ответов — JSON в UTF-8.
Шифрования сервер не делает: в домашней сети планер говорит с ним напрямую
(`192.168.x.x:8765`), а для выхода в интернет перед сервером ставится обратный
прокси с TLS, и в планере указывается адрес `https://…`.

Ошибка — всегда `{"error": "<код>", "message": "<текст по-русски>"}` с
кодом HTTP. Код — для программы, текст — для человека: планер показывает его
как есть.

### 3.2 Аккаунт и сеанс

- `POST /api/register` и `POST /api/login` возвращают **ключ сеанса**; планер
  хранит его в настройках устройства (`settings.ini`) вместе с адресом сервера
  и логином и шлёт в каждом запросе: `Authorization: Bearer <ключ>`.
- Ответ 401 значит, что ключ больше не действует (выход, смена пароля на
  другом устройстве, год без синхронизации, аккаунт удалён): планер забывает
  ключ и просит войти снова.
- В одном планере может быть несколько аккаунтов, в том числе на разных
  серверах; у каждого свой файл базы на устройстве.

### 3.3 Запись

Единица обмена — запись планера:

```json
{ "kind": "task", "id": "…", "modified": 1790000000000, "deleted": false, "data": { … } }
```

- `kind` — вид записи (`^[a-z_]{1,32}$`): `calendar`, `event`, `task`,
  `completion`, `melody`, `alarmstop`, `habit`, `habitmark`, `reminder`;
  `category` остался на старых серверах от прежних версий планера и
  пропускается при разборе.
- `id` — идентификатор записи в планере, до 200 символов. Записи, которые
  могут появиться на двух устройствах независимо (отметка привычки за день,
  выключенный будильник), получают id из своего смысла, а не случайный — тогда
  два устройства пишут одну запись, а не две.
- `modified` — момент правки в миллисекундах от эпохи, его ставит устройство.
- `data` — JSON записи **в формате резервной копии планера**
  (`JsonIo::toJson()`); у удаления его нет. Сервер его не разбирает, поэтому
  новый вид или новое поле — забота одного планера.

### 3.4 Обмен

`POST /api/sync` — один запрос в обе стороны:

1. Устройство присылает `since` — курсор, ревизию сервера, до которой оно уже
   в курсе, — и `changes`: всё, что изменилось у него с прошлого обмена
   (журнал изменений планера), в нынешнем виде записей.
2. Сервер применяет изменения по порядку. Для каждой записи побеждает
   **более поздняя правка** по `modified`; проигравшая отклоняется, и
   серверная версия возвращается устройству.
3. В ответе — `revision` (новый курсор), `changes` (всё новее `since`, кроме
   только что принятого от этого устройства), счётчики `accepted` /
   `rejected` и `conflicts` (3.6).
4. Устройство применяет пришедшее **без журнала** (чтобы не отправить эхо
   обратно) и снимает из журнала подтверждённые строки — только те, что не
   новее отправленного: правка, сделанная, пока запрос был в пути, уйдёт
   следующим обменом.

Первый обмен нового устройства идёт с `since = 0`: оно получает весь аккаунт,
но без надгробий удалённых записей — удалять ему нечего. Если аккаунт уже не
пуст, планер при этом убирает свой «посев» — первый календарь, который каждое
устройство заводит само.

**Когда обмен идёт** — решает планер: через 3 секунды после правки, раз в
выбранный промежуток (по умолчанию 15 минут), при возвращении приложения
вперёд и при уходе в фон, если что-то ждёт отправки; после обрыва связи —
пингом с растущей паузой, и сразу, как только сервер ответил.

**Одна запись перед правкой.** Прежде чем открыть запись в редакторе, планер
спрашивает её одну — `GET /api/record?kind=…&id=…`, — чтобы не затереть
правку, сделанную минуту назад на другом устройстве. Курсор при этом не
двигается, а более поздняя местная правка из журнала выигрывает и у этого
ответа. Сервер, которому этот запрос неизвестен, отвечает 404, и планер ждёт
обычного обмена.

**Повторная выгрузка.** Если сервер потерял то, что уже подтвердил (аккаунт
создан заново, базу заменили), обе стороны считают, что обменялись всем, и
сами записи не уедут никогда. Планер замечает это по нулевому курсору при
непустом устройстве и предлагает «Выгрузить всё заново»: кладёт в журнал
каждую запись и обнуляет курсор.

### 3.5 Общие календари

Владелец открывает **свой** календарь другим аккаунтам, и попасть в него можно
только по ссылке:

1. Владелец включает доступ и выбирает режим — все читают, все правят или
   права по одному (`POST /api/share`, `/api/share/member`) — и получает
   ссылку (`POST /api/share/link`), одноразовую или многоразовую, со сроком
   или без.
2. Планер владельца отдаёт её как
   `calendar-planner://share?server=<адрес>&token=<токен>`. На Android схема
   объявлена в манифесте, на компьютере ссылка передаётся аргументом
   командной строки.
3. Планер участника показывает, куда ведёт ссылка (`GET /api/share/peek`), и
   заводит **календарь-близнец** — свой календарь со своим id, названием и
   цветом. `POST /api/share/join` с `twinId` впускает участника, и сервер
   копирует содержимое календаря в записи его аккаунта — дальше его
   приносит обычный обмен.
4. Правка общей записи кем угодно расходится по всем: сервер кладёт её
   владельцу и каждому участнику, подменяя `calendarId` на тот, которым
   календарь зовётся у получателя. Это единственное место, где сервер
   заглядывает внутрь записи. Ходят так события, задачи и журнал выполнений;
   объект календаря владельца — никогда.
5. Право участника приезжает в записи его близнеца (поле `access`): планер
   участника видит только свои записи, и повышение или понижение прав
   доходит до него тем же обменом.
6. Уход (`POST /api/share/leave`) или исключение владельцем — сервер ставит
   на копиях участника надгробия, и они исчезают со всех его устройств.
   Планер участника убирает содержимое близнеца **без журнала**: иначе
   удаление каждой записи уехало бы на сервер как правка общего календаря и
   стёрло бы её у владельца.

Напоминания владельца в близнец не едут: планер участника подставляет в
пришедшую запись свои напоминания. Напоминание — дело человека, а не записи.

### 3.6 Конфликты

Правка общего календаря, которую сервер применить не может, возвращается в
`conflicts` с причиной и самой правкой:

| `reason` | Когда | Что делает планер |
|---|---|---|
| `read_only` | у участника только чтение | показывает, что правка не сохранена; версия владельца возвращается сама |
| `deleted` | владелец удалил запись, пока участник её правил | спрашивает: вернуть запись с правкой или отказаться; «вернуть» отправляет её снова с `"restore": true` |

Обе проверки сервер делает **раньше** правила «побеждает более поздняя»: это
вопросы пользователю, а правило молчит. Участник, правивший запись без сети,
иначе терял бы работу без единого слова.

### 3.7 Маршруты

| Запрос | Кто зовёт и когда |
|---|---|
| `GET /api/ping` | «Проверить сервер» в настройках (несколько запросов подряд — время ответа), проверка связи после обрыва |
| `POST /api/register`, `/api/login`, `/api/logout` | вход и выход в панели аккаунта |
| `GET /api/me` | есть в `SyncClient`, интерфейс его пока не зовёт |
| `POST /api/profile`, `/api/password` | в планере пока нет; пароль меняет администратор (`--set-password`) |
| `POST /api/sync` | служба синхронизации |
| `GET /api/record` | перед правкой записи |
| `GET`/`POST /api/share`, `/api/share/member`, `/api/share/link` | блок совместного доступа в карточке своего календаря |
| `GET /api/share/peek`, `POST /api/share/join` | переход по ссылке |
| `POST /api/share/leave` | «Отказаться от доступа» |

Тела запросов и ответов — в README сервера, раздел «API».

## 4. Данные

| Где | Файл | Что |
|---|---|---|
| устройство, без аккаунта | `planner.db` | весь локальный планер; на сервер не попадает никогда |
| устройство, аккаунт | `accounts/<ключ>.db` | копия планера аккаунта, журнал изменений `sync_journal`, курсор |
| устройство | `settings.ini` | настройки, список аккаунтов с ключами сеансов |
| сервер | `server.db` | аккаунты, хеши паролей и ключей, записи всех аккаунтов (с надгробиями), общие календари и хеши ссылок |

Папки данных по умолчанию: на Windows — `%APPDATA%\CalendarPlanner\CalendarPlanner`
и `%APPDATA%\CalendarPlanner\CalendarServer`, на Linux —
`~/.local/share/CalendarPlanner/…`, на Android — песочница приложения. Обе
программы переносят папку ключом `--data-dir`.

**Резервные копии.** У планера — JSON всей базы («Настройки → Данные»), он же
формат `data` в обмене. У сервера — копия `server.db` при остановленном
сервере.

## 5. Версии и совместимость

| Что | Где задано | Сейчас |
|---|---|---|
| версия API сервера | `Api::apiVersion()`, поле `api` в `ping` | 1 |
| схема базы сервера | `PRAGMA user_version` `server.db` | 2 |
| схема базы планера | `PRAGMA user_version` `planner.db` | 14 |
| формат резервной копии планера (и `data` записей) | `JsonIo` | 11 |
| версии программ | `project(... VERSION)` в `CMakeLists.txt` | планер 1.0.0, сервер 1.0.0 |

Правила, на которых держится совместимость:

- **Новый вид записи или новое поле** меняют только планер: сервер хранит их
  как есть. Старый планер пропускает неизвестный вид при разборе, а
  неизвестное поле — при чтении JSON.
- **Новый маршрут** сервера планер должен пережить отсутствие: старый сервер
  отвечает на него 404 (так сделано с `/api/record`).
- **Несовместимое изменение протокола** поднимает версию API. Планер её пока
  не сверяет — в ответе `ping` он смотрит только `service`, — поэтому вместе с
  таким изменением в планер добавляется и проверка поля `api`.
- Обе базы дотягиваются до текущей схемы сами при открытии; понижать версию
  программы поверх новой базы нельзя.

## 6. Развёртывание

- **Дома.** Сервер на компьютере в домашней сети (Windows — `run-server.bat`
  или задача планировщика; Linux — служба `deploy/calendar-server.service`),
  порт 8765 открыт в брандмауэре для частной сети. Планеры вводят адрес вида
  `192.168.0.146:8765`; сервер печатает свои адреса при старте.
- **Снаружи.** Сервер за обратным прокси с TLS; в планере — `https://…`.
  Регистрацию после заведения своих аккаунтов можно закрыть
  (`--no-registration`).
- **Телефон без Wi-Fi до сервера** (отладка) — `adb reverse tcp:8765 tcp:8765`
  и адрес `127.0.0.1:8765` на телефоне.

Поставка: `build-packages.bat` собирает в `Build/` установщики Windows (MSI
и setup.exe планера и сервера) и APK, подписанный ключом выпуска; пакетов
Linux пока нет — сервер там ставится из исходников (`cmake --install`) со
службой из `deploy/`. Подробности и что дальше — в [PACKAGING.md](PACKAGING.md).

## 7. Проверка связки

- **Сервер сам по себе** — его 22 теста поднимают его в процессе и говорят с
  ним по HTTP, включая общие календари целиком.
- **Планер сам по себе** — его тесты гоняют два хранилища через поддельный
  сервер (`SyncEngine` без сети).
- **Вместе** — тест планера `syncServiceTalksToRealServer` регистрирует аккаунт
  на запущенном сервере и гоняет через него `SyncService` двух устройств; без
  переменной `PLANNER_TEST_SERVER=<адрес>` он пропускается.
- **Вручную** — тестовый аккаунт на отдельном экземпляре сервера (свой порт и
  `--data-dir`), на телефоне — в песочнице планера; после проверки выход из
  аккаунта убирает его копию с устройства.

## 8. Чего нет

- часовых поясов: даты и время планера — локальные, сервер их не трогает;
- шифрования без прокси, слияния полей при конфликте, истории правок;
- синхронизации с внешними календарями (CalDAV) — только импорт и экспорт ICS;
- приглашения в общий календарь по логину — только по ссылке, это решение:
  сервер не раскрывает, какие логины у него есть.
