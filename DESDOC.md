# Космос календарь — устройство системы

Документ описывает систему целиком: из каких частей она состоит, как планер и
сервер говорят друг с другом, где какие данные и как части развёртываются и
совмещаются по версиям. Внутреннее устройство каждой части — в её собственном
документе:

- планер — [`Calendar/DesDoc.md`](Calendar/DesDoc.md)
  ([SayxZero/Calendar](https://github.com/SayxZero/Calendar));
- сервер — [`CalendarServer/DesDoc.md`](CalendarServer/DesDoc.md)
  ([SayxZero/CalendarServer](https://github.com/SayxZero/CalendarServer));
- сайт — [`CalendarWeb/DesDoc.md`](CalendarWeb/DesDoc.md)
  ([SayxZero/CalendarWeb](https://github.com/SayxZero/CalendarWeb));
- бэкенд сайта — [`CalendarWebServer/DesDoc.md`](CalendarWebServer/DesDoc.md)
  ([SayxZero/CalendarWebServer](https://github.com/SayxZero/CalendarWebServer)).

Здесь их устройство не повторяется — только то, что на стыке.

| **Сайт** (`CalendarWeb/`) | планер в браузере для аккаунта: те же экраны, записи, повторения, напоминания (пока вкладка открыта), общий доступ, ICS, палитры; раскладки для ПК и телефона | современные браузеры | нет: ES-модули и CSS без сборки; тесты — Node.js 20+ |

Планер и сервер — Qt 6 / C++17, без сторонних библиотек, каждый собирается
CMake и qmake. Код у них общий только по смыслу: сервер не подключает
исходников планера и наоборот, их связывает один протокол.

**Сайт — ещё одно устройство аккаунта.** Его логика — перенос логики планера
на JS (повторения, хранилище, обмен, формат записей `JsonIo`, ICS), а говорит
он с сервером тем же протоколом, через бэкенд. Ни сайт, ни бэкенд не
открывают `server.db`: все правила — ревизии, «побеждает более поздняя
правка», общие календари, защита входа — остаются в сервере синхронизации, и
он о сайте не знает. Бэкенд добавляет только то, без чего браузер нельзя
пускать к API напрямую (раздел 3.8).

**Планер главный.** Без аккаунта он сети не касается вовсе и работает с
локальной базой. Аккаунт — это ещё один файл базы на устройстве и фоновая
служба, которая держит его в согласии с сервером; интерфейс работает с базой
одинаково в обоих случаях. Сервер поэтому необязателен, и его недоступность
не мешает работе: правки копятся в журнале устройства и уходят, когда связь
вернётся.

**Админ-панель — не часть протокола.** Это программа администратора рядом с
сервером: файл его базы она читает напрямую, на своём соединении SQLite рядом
с работающим сервером, а службу запускает и останавливает через диспетчер
служб. Планеру она не нужна, сервер о ней не знает; общий у них только код
чтения базы (панель собирается из исходников сервера). Записи планеров панель
показывает по нескольким полям их формата — название, календарь, момент, — и
целиком как JSON.

## 3. Протокол

### 3.1 Транспорт

HTTP/1.1 с постоянными соединениями, тела запросов и ответов — JSON в UTF-8.
Шифрования сервер не делает: в домашней сети планер говорит с ним напрямую
(`192.168.x.x:8765`), а для выхода в интернет перед сервером ставится обратный
прокси с TLS, и в планере указывается адрес `https://…`.

Ошибка — всегда `{"error": "<код>", "message": "<текст по-русски>"}` с
кодом HTTP. Код — для программы, текст — для человека: планер показывает его
как есть.

Ответ на обмен уходит, когда его правки уже на диске (`sync_mode = full`,
по умолчанию); правки разных устройств сервер фиксирует пачками — одним
сбросом на диск на всех, кто пришёл, пока шёл предыдущий. С `sync_mode =
normal` ответ может опередить сброс, и при отключении питания сервер потеряет
обмены последних секунд, которые устройства считают принятыми, — как после
восстановления из копии.

Под нагрузкой сервер замедляется, а не отказывает: соединения сверх предела
ждут в очереди системы, а запросы — свободного потока. Отказ один —
`503 {"error": "overloaded"}` с `Retry-After`: очередь запросов полна или
запрос прождал дольше, чем клиент ждёт ответа (30 секунд; у планера обмен
ждёт 60, остальные запросы 15). Планер принимает его как любую ошибку
сервера — показывает текст и повторяет обмен через 15, 30, 60 и 120 секунд.
Сервер может закрыть простаивающее соединение, когда соединений слишком
много; клиент открывает новое.

### 3.2 Аккаунт и сеанс

- `POST /api/register` и `POST /api/login` возвращают **ключ сеанса**; планер
  хранит его в настройках устройства (`settings.ini`) вместе с адресом сервера
  и логином и шлёт в каждом запросе: `Authorization: Bearer <ключ>`.
- Ответ 401 значит, что ключ больше не действует (выход, смена пароля на
  другом устройстве, год без синхронизации, аккаунт удалён, сеансы завершены
  из админ-панели): планер забывает ключ и просит войти снова. Схема `Bearer`
  принимается в любом регистре.
- Неверные пароли блокируют вход на 10 минут по паре «адрес и логин» (10
  неудач) и по адресу в целом (50), ответ — 429; так за одним прокси или
  роутером опечатки одного человека не закрывают вход остальным.
- Неизвестный маршрут — 404, известный не тем методом — 405; это решается до
  проверки ключа.
- В одном планере может быть несколько аккаунтов, в том числе на разных
  серверах; у каждого свой файл базы на устройстве.

### 3.3 Запись

Единица обмена — запись планера:

```json
{ "kind": "task", "id": "…", "modified": 1790000000000, "deleted": false, "data": { … } }
```

- `kind` — вид записи (`^[a-z_]{1,32}$`): `calendar`, `event`, `task`,
  `completion`, `melody`, `alarmstop`, `habit`, `habitmark`, `reminder`;
  `category` остался на старых серверах от прежних версий планера и
  пропускается при разборе.
- `id` — идентификатор записи в планере, до 200 символов. Записи, которые
  могут появиться на двух устройствах независимо (отметка привычки за день,
  выключенный будильник), получают id из своего смысла, а не случайный — тогда
  два устройства пишут одну запись, а не две.
- `modified` — момент правки в миллисекундах от эпохи, его ставит устройство.
  Момент, опережающий часы сервера больше чем на 10 минут, сервер заменяет
  своим временем: устройство со сбитыми часами иначе перебивало бы правки
  остальных, пока его часы не вернутся.
- `data` — JSON записи **в формате резервной копии планера**
  (`JsonIo::toJson()`); у удаления его нет. Сервер его не разбирает, поэтому
  новый вид или новое поле — забота одного планера.

### 3.4 Обмен

`POST /api/sync` — один запрос в обе стороны:

1. Устройство присылает `since` — курсор, ревизию сервера, до которой оно уже
   в курсе, — и `changes`: всё, что изменилось у него с прошлого обмена
   (журнал изменений планера), в нынешнем виде записей.
2. Сервер применяет изменения по порядку. Для каждой записи побеждает
   **более поздняя правка** по `modified`; проигравшая отклоняется, и
   серверная версия возвращается устройству.
3. В ответе — `revision` (новый курсор), `changes` (всё новее `since`, кроме
   только что принятого от этого устройства), счётчики `accepted` /
   `rejected` и `conflicts` (3.6).
4. Устройство применяет пришедшее **без журнала** (чтобы не отправить эхо
   обратно) и снимает из журнала подтверждённые строки — только те, что не
   новее отправленного: правка, сделанная, пока запрос был в пути, уйдёт
   следующим обменом.

Первый обмен нового устройства идёт с `since = 0`: оно получает весь аккаунт,
но без надгробий удалённых записей — удалять ему нечего. Если аккаунт уже не
пуст, планер при этом убирает свой «посев» — первый календарь, который каждое
устройство заводит само.

**Когда обмен идёт** — решает планер: через 3 секунды после правки, раз в
выбранный промежуток (по умолчанию 15 минут), при возвращении приложения
вперёд и при уходе в фон, если что-то ждёт отправки; после обрыва связи —
пингом с растущей паузой, и сразу, как только сервер ответил.

**Одна запись перед правкой.** Прежде чем открыть запись в редакторе, планер
спрашивает её одну — `GET /api/record?kind=…&id=…`, — чтобы не затереть
правку, сделанную минуту назад на другом устройстве. Курсор при этом не
двигается, а более поздняя местная правка из журнала выигрывает и у этого
ответа. Сервер, которому этот запрос неизвестен, отвечает 404, и планер ждёт
обычного обмена.

**Повторная выгрузка.** Если сервер потерял то, что уже подтвердил (аккаунт
создан заново, базу заменили), обе стороны считают, что обменялись всем, и
сами записи не уедут никогда. Планер замечает это по нулевому курсору при
непустом устройстве и предлагает «Выгрузить всё заново»: кладёт в журнал
каждую свою запись и обнуляет курсор. Записи чужих календарей (близнецов)
остаются в стороне: их хранит владелец, сервер раздаст копии сам, а отправленные
участником они стёрли бы напоминания владельца.

### 3.5 Общие календари

Владелец открывает **свой** календарь другим аккаунтам, и попасть в него можно
только по ссылке:

1. Владелец включает доступ и выбирает режим — все читают, все правят или
   права по одному (`POST /api/share`, `/api/share/member`) — и получает
   ссылку (`POST /api/share/link`), одноразовую или многоразовую, со сроком
   или без.
2. Планер владельца отдаёт её как
   `calendar-planner://share?server=<адрес>&token=<токен>`. На Android схема
   объявлена в манифесте, на компьютере ссылка передаётся аргументом
   командной строки — запущенному планеру, если он уже работает. Токен
   понятен только серверу из ссылки: планер участника открывает её в
   аккаунте на этом сервере, а без такого аккаунта предлагает войти или
   зарегистрироваться там и продолжает после входа.
3. Планер участника показывает, куда ведёт ссылка (`GET /api/share/peek`), и
   заводит **календарь-близнец** — свой календарь со своим id, названием и
   цветом. `POST /api/share/join` с `twinId` впускает участника, и сервер
   копирует содержимое календаря в записи его аккаунта — дальше его
   приносит обычный обмен.
4. Правка общей записи кем угодно расходится по всем: сервер кладёт её
   владельцу и каждому участнику, подменяя `calendarId` на тот, которым
   календарь зовётся у получателя. Это единственное место, где сервер
   заглядывает внутрь записи. Ходят так события, задачи и журнал выполнений;
   объект календаря владельца — никогда.
5. Право участника приезжает в записи его близнеца (поле `access`): планер
   участника видит только свои записи, и повышение или понижение прав
   доходит до него тем же обменом.
6. Уход (`POST /api/share/leave`) или исключение владельцем — сервер ставит
   на копиях участника надгробия, и они исчезают со всех его устройств.
   Планер участника убирает содержимое близнеца **без журнала**: иначе
   удаление каждой записи уехало бы на сервер как правка общего календаря и
   стёрло бы её у владельца.

Напоминания владельца в близнец не едут: планер участника подставляет в
пришедшую запись свои напоминания. Напоминание — дело человека, а не записи.
Список владельца планер участника при этом откладывает и, когда участник
правит запись, отправляет её с ним, а не со своим: иначе каждая правка
участника стирала бы напоминания владельца.

### 3.6 Конфликты

Правка общего календаря, которую сервер применить не может, возвращается в
`conflicts` с причиной и самой правкой:

| `reason` | Когда | Что делает планер |
|---|---|---|
| `read_only` | у участника только чтение | показывает, что правка не сохранена; версия владельца возвращается сама |
| `deleted` | владелец удалил запись, пока участник её правил | спрашивает: вернуть запись с правкой или отказаться; «вернуть» отправляет её снова с `"restore": true` |

Обе проверки сервер делает **раньше** правила «побеждает более поздняя»: это
вопросы пользователю, а правило молчит. Участник, правивший запись без сети,
иначе терял бы работу без единого слова.

### 3.7 Маршруты

| Запрос | Кто зовёт и когда |
|---|---|
| `GET /api/ping` | «Проверить сервер» в настройках (несколько запросов подряд — время ответа), проверка связи после обрыва |
| `POST /api/register`, `/api/login`, `/api/logout` | вход и выход в панели аккаунта |
| `GET /api/me` | есть в `SyncClient`, интерфейс его пока не зовёт |
| `POST /api/profile`, `/api/password` | в планере пока нет; пароль меняет администратор (`--set-password`) |
| `POST /api/sync` | служба синхронизации |
| `GET /api/record` | перед правкой записи |
| `GET`/`POST /api/share`, `/api/share/member`, `/api/share/link` | блок совместного доступа в карточке своего календаря |
| `GET /api/share/peek`, `POST /api/share/join` | переход по ссылке |
| `POST /api/share/leave` | «Отказаться от доступа» |

Тела запросов и ответов — в README сервера, раздел «API». Сайт зовёт те же
маршруты в тех же местах, что планер (через бэкенд, раздел 3.8).

### 3.8 Сайт и его бэкенд

Браузер говорит с бэкендом (`CalendarWebServer`), бэкенд — с сервером
синхронизации тем же протоколом, что планер:

- **Ключ сеанса — в cookie** `cosmos_session` (`HttpOnly`, `SameSite=Strict`,
  `Secure` за HTTPS). Ответ на вход и регистрацию бэкенд передаёт странице без
  ключа, остальные запросы снабжает `Authorization: Bearer`; ответ 401 стирает
  cookie, и сайт просит войти снова, как планер.
- **Только маршруты планера** (таблица `ApiRoutes`), изменяющий запрос — только
  со страницы сайта (свой заголовок `X-Requested-With`, свой `Origin`).
- **Неверные пароли** бэкенд считает сам, по адресу посетителя (5 на логин,
  20 на адрес за 10 минут): сервер считает по адресу соединения, а он у всех
  посетителей сайта один — адрес бэкенда.
- **Ссылка общего доступа** с сайта бывает двух видов: для сайта
  (`https://<сайт>/#join=<токен>`) и для планера (`calendar-planner://share?…`
  с адресом сервера из настройки `--public-server` бэкенда). Токен — один и
  тот же, понимает его сервер синхронизации.
- **Имя устройства** в сеансах сервера — «Сайт · <браузер> на <система>».

## 4. Данные

| Где | Файл | Что |
|---|---|---|
| устройство, без аккаунта | `planner.db` | весь локальный планер; на сервер не попадает никогда |
| устройство, аккаунт | `accounts/<ключ>.db` | копия планера аккаунта, журнал изменений `sync_journal`, курсор |
| устройство | `settings.ini` | настройки, список аккаунтов с ключами сеансов |
| браузер | IndexedDB `cosmos-<логин>` | копия аккаунта для сайта: записи, журнал изменений, курсор; удаляется при выходе |
| браузер | `localStorage`, cookie `cosmos_session` | настройки сайта на этом устройстве; ключ сеанса (страница его не видит) |
| сервер | `server.db` | аккаунты, хеши паролей и ключей, записи всех аккаунтов (с надгробиями), общие календари и хеши ссылок, обмены по дням (для статистики) |
| сервер | `server.ini`, `server.log` | настройки службы и её журнал |
| сервер | `metrics.db` | нагрузка: по минутам за неделю, по часам за год; в резервные копии не входит |

Папки данных по умолчанию: у планера на Windows —
`%APPDATA%\CalendarPlanner\CalendarPlanner`, на Linux —
`~/.local/share/CalendarPlanner/…`, на Android — песочница приложения. Сервер,
поставленный установщиком, работает службой с папкой
`%ProgramData%\CalendarPlanner\CalendarServer` (её открывают только
администраторы и сама служба); сервер в консоли без настроек — с
`%APPDATA%\CalendarPlanner\CalendarServer`, на Linux служба systemd — с
`/var/lib/calendar-server`. Обе программы переносят папку ключом `--data-dir`.

**Резервные копии.** У планера — JSON всей базы («Настройки → Данные»), он же
формат `data` в обмене. У сервера — копии из админ-панели: снимаются на ходу
(`VACUUM INTO`), лежат в `backups\` папки данных, и восстановление оттуда же.
После восстановления устройства об откате не знают: то, что на них менялось
после копии, они не пришлют сами — для этого в планере «Выгрузить всё
заново…». Счётчик ревизий аккаунтов при восстановлении не уходит назад, иначе
устройства пропускали бы и новые изменения.

## 5. Версии и совместимость

| Что | Где задано | Сейчас |
|---|---|---|
| версия API сервера | `Api::apiVersion()`, поле `api` в `ping` | 1 |
| схема базы сервера | `PRAGMA user_version` `server.db` | 3 |
| схема базы планера | `PRAGMA user_version` `planner.db` | 14 |
| формат резервной копии планера (и `data` записей) | `JsonIo` | 11 |
| версии программ | `project(... VERSION)` в `CMakeLists.txt` | планер 1.1.0, сервер и админ-панель 1.3.0 |
| версии сайта и бэкенда | `package.json`, `<Version>` в `CalendarWebServer.csproj` | 1.0.0 и 1.0.0; формат записей — как у планера (11) |

Правила, на которых держится совместимость:

- **Новый вид записи или новое поле** меняют только планер: сервер хранит их
  как есть. Старый планер пропускает неизвестный вид при разборе, а
  неизвестное поле — при чтении JSON.
- **Новый маршрут** сервера планер должен пережить отсутствие: старый сервер
  отвечает на него 404 (так сделано с `/api/record`). Сайту новый маршрут
  становится доступен, только когда его добавят в белый список бэкенда.
- **Новое поле записи** сайт сохраняет, даже не зная его (неизвестные поля
  `normalize()` не трогает), но показывает и правит, только когда его
  добавят в модель сайта.
- **Несовместимое изменение протокола** поднимает версию API. Планер её пока
  не сверяет — в ответе `ping` он смотрит только `service`, — поэтому вместе с
  таким изменением в планер добавляется и проверка поля `api`.
- Обе базы дотягиваются до текущей схемы сами при открытии; понижать версию
  программы поверх новой базы нельзя. Сервер сам отказывается открыть базу
  более новой схемы.
- Админ-панель и сервер — одной версии, из одного установщика; панель схему
  не меняет и базу старой схемы (без таблицы активности) читает без статистики,
  а без `metrics.db` (сервер до 1.3) — без нагрузки.

## 6. Развёртывание

- **Дома.** Сервер на компьютере в домашней сети. На Windows установщик
  ставит его службой `CosmosCalendarServer`: без окна, с запуском вместе с
  системой и сразу после установки, с правилом брандмауэра для частных сетей;
  запускает, останавливает и показывает его админ-панель. Сервер прежней
  версии, работавший в консоли, установщик закрывает, а его базу служба
  забирает себе копией, пока у неё нет своих аккаунтов. Для разработки —
  по-прежнему `run-server.bat`. На Linux — служба
  `deploy/calendar-server.service`. Планеры вводят адрес вида
  `192.168.0.146:8765`; его показывают и админ-панель, и журнал сервера.
- **Настройки нагрузки** (потоки, очередь, групповая запись, сброс на диск,
  память) зависят от машины, и сильнее всего — от диска: на жёстком диске
  правки упираются в сброс, на SSD — в процессор. Их подбирает бенчмарк
  `CalendarServerBench`, который ставится вместе с сервером, — со страницы
  «Многопоточность» админ-панели, пока сервер остановлен.
- **Один сервер на базу.** Сервер держит `server.lock` в папке данных и пишет
  рядом `server.run` (процесс, порт, журнал): второй сервер на ту же папку не
  запустится, а админ-панель по ним находит сервер своей папки и не
  восстанавливает копию поверх базы, с которой он работает.
- **Снаружи.** Сервер за обратным прокси с TLS; в планере — `https://…`.
  Регистрацию после заведения своих аккаунтов можно закрыть
  (`--no-registration`).
- **Телефон без Wi-Fi до сервера** (отладка) — `adb reverse tcp:8765 tcp:8765`
  и адрес `127.0.0.1:8765` на телефоне.
- **Сайт.** Бэкенд — рядом с сервером синхронизации (`-u 127.0.0.1:8765
  --public-server 192.168.0.146:8765`) или на другой машине; ему не нужны ни
  права, ни доступ к базе — только порт сервера. Наружу — за обратным прокси с
  TLS, бэкенд слушает `127.0.0.1` и знает прокси (`--trusted-proxy`). Готовая
  папка — `CalendarWebServer\publish.bat` (сервер и `site\` рядом), нужен
  ASP.NET Core Runtime 10. В пакеты выпуска сайт пока не входит.

Поставка: `build-packages.bat` собирает в `Build/` установщики Windows (MSI
и setup.exe планера и сервера) и APK, подписанный ключом выпуска; пакетов
Linux пока нет — сервер там ставится из исходников (`cmake --install`) со
службой из `deploy/`. Подробности и что дальше — в [PACKAGING.md](PACKAGING.md).

## 7. Проверка связки

- **Сервер сам по себе** — его 27 тестов поднимают его в процессе и говорят с
  ним по HTTP, включая общие календари целиком, счёт обменов, копии и перенос
  базы; ещё 10 (`tst_admin`) проверяют, что админ-панель читает из базы,
  новый пароль, копии с восстановлением и командную строку службы.
- **Планер сам по себе** — его тесты гоняют два хранилища через поддельный
  сервер (`SyncEngine` без сети).
- **Вместе** — тест планера `syncServiceTalksToRealServer` регистрирует аккаунт
  на запущенном сервере и гоняет через него `SyncService` двух устройств; без
  переменной `PLANNER_TEST_SERVER=<адрес>` он пропускается.
- **Вручную** — тестовый аккаунт на отдельном экземпляре сервера (свой порт и
  `--data-dir`), на телефоне — в песочнице планера; после проверки выход из
  аккаунта убирает его копию с устройства.
- **Сайт** — 56 тестов логики (`node --test`: повторения, формат записей,
  хранилище, обмен двух устройств через поддельный сервер, ICS) и 24 теста
  бэкенда (`dotnet test`: прокси, cookie, защита, раздача; один — с настоящим
  сервером при `WEB_TEST_SERVER=<адрес>`). Вместе — сайт во встроенном
  браузере перед тестовым сервером, а правка с сайта — в настоящем планере в
  песочнице (`CalendarWeb/CLAUDE.md`, «Проверка в браузере»).

## 8. Чего нет

- часовых поясов: даты и время планера — локальные, сервер их не трогает;
- шифрования без прокси, слияния полей при конфликте, истории правок;
- синхронизации с внешними календарями (CalDAV) — только импорт и экспорт ICS;
- фоновых напоминаний сайта: он напоминает, пока его вкладка открыта;
- приглашения в общий календарь по логину — только по ссылке, это решение:
  сервер не раскрывает, какие логины у него есть.
