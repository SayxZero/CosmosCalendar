## Что здесь

**CosmosCalendar** — зонтичный репозиторий «Космос календаря». Код живёт в
пяти сабмодулях, у каждого свой репозиторий, своя история и своя
документация:

| Папка | Репозиторий | Что это |
|---|---|---|
| `Calendar/` | [SayxZero/Calendar](https://github.com/SayxZero/Calendar) | планер: Qt 6 / C++17, Windows, Linux, Android |
| `CalendarServer/` | [SayxZero/CalendarServer](https://github.com/SayxZero/CalendarServer) | сервер синхронизации (Qt 6 Core, Network, Sql; служба Windows и Linux) и его админ-панель (Qt Widgets) |
| `CalendarWeb/` | [SayxZero/CalendarWeb](https://github.com/SayxZero/CalendarWeb) | сайт — презентация и планер в браузере: ES-модули и CSS без сборки и библиотек, тесты `node --test` |
| `CalendarWebServer/` | [SayxZero/CalendarWebServer](https://github.com/SayxZero/CalendarWebServer) | бэкенд сайта на ASP.NET Core (.NET 10): отдаёт сайт и передаёт его запросы серверу синхронизации по HTTP API, ключ сеанса — в HttpOnly-cookie |
| `CalendarWebMCP/` | [SayxZero/CalendarWebMCP](https://github.com/SayxZero/CalendarWebMCP) | облачный режим MCP: служба на Node.js с логикой сайта, агент работает с аккаунтом как ещё одно устройство |

Сайт — ещё одно устройство аккаунта: своей базы у него и у бэкенда нет,
записи те же, что у планеров, и в том же формате (`JsonIo` планера). Почему
через HTTP API, а не прямо к `server.db`, — `CalendarWebServer/DesDoc.md`,
раздел 1.1.

Здесь лежит только то, что касается нескольких частей сразу:

- [DESDOC.md](DESDOC.md) — как планер и сервер работают вместе: состав системы,
  протокол, где какие данные, развёртывание и совместимость версий;
- [ISSUES.md](ISSUES.md) — грабли, на которые уже наступали (подгружается ниже);
- [PACKAGING.md](PACKAGING.md) — установочные пакеты: сборка, содержимое,
  что дальше;
- `build-packages.ps1` (и `build-packages.bat`) — все пакеты выпуска одной
  командой (ниже);
- [README.md](README.md) — что это и как получить всё одной командой.

Работа над кодом идёт в сабмодулях. У каждого свои `CLAUDE.md` (у планера —
подробный, с архитектурой и соглашениями), `README.md` и `DesDoc.md`.
**Разделение документов:** DesDoc планера не описывает внутреннее устройство
сервера, DesDoc сервера — устройство планера; то, как они говорят друг с
другом, может быть в обоих, а целиком описано в `DESDOC.md` здесь. Так же с
README: о самом проекте подробно, о соседнем — минимум и ссылка. Сайт и его
бэкенд — так же.

**Логика сайта — порт логики планера** (повторения, `DataStore`, `SyncEngine`,
`JsonIo`, `IcsIo` — в `CalendarWeb/site/js`). Правка формата записи или
правил хранилища в планере требует той же правки на сайте; таблица
соответствия файлов — `CalendarWeb/DesDoc.md`, раздел 2.

**MCP — два режима с одним набором инструментов.** Локальный живёт в планере
(`Calendar/src/core/mcp*`, мост `Calendar/tools/mcpbridge`, инструкция
`Calendar/docs/MCP.md`, которую установщик кладёт рядом с программой), облачный — в
`CalendarWebMCP` (инструкция `docs/MCP-Web.md`), а вход агента — в бэкенде сайта.
Правка инструмента — в `mcptooldefs.h` и `tools.json` (тест сверяет), в `mcptools.cpp` и
`tools.js`, в обеих инструкциях; обе инструкции копируются в `CalendarWeb/site/docs`
(тест сверяет и это).

## Репозитории и коммиты

- **Коммитить и пушить — только когда об этом попросили.**
- **Сначала сабмодуль, потом зонтик.** Коммит и push делаются в сабмодуле, и
  только потом здесь коммитится его новый указатель (`git add Calendar`).
  Указатель на коммит, которого нет на GitHub, ломает
  `git clone --recursive` и `git submodule update` всем остальным.
- **Ветка у всех шести — `master`**, в `.gitmodules` она прописана, так что
  `git submodule update --remote` берёт именно её.
- **Свежая копия** — `git clone --recursive https://github.com/SayxZero/CosmosCalendar.git`;
  в уже склонированной без сабмодулей — `git submodule update --init`.
- **После `git submodule update` сабмодуль стоит на оторванной голове.** Перед
  правками в нём — `git switch master`, иначе коммит повиснет вне ветки.
- Каталоги `.git` сабмодулей лежат в `.git/modules/` зонтичного репозитория, а
  `Calendar/.git` — файл со ссылкой туда. git внутри `Calendar/`,
  `CalendarServer/`, `CalendarWeb/` и `CalendarWebServer/` работает как в
  обычном репозитории. Сабмодуль, созданный прямо в рабочей копии
  (`git init` в папке, потом `git submodule add <url> <папка>`), держит свой
  `.git` у себя, пока его не перенесёт `git submodule absorbgitdirs <папка>`.
- `.gitignore` у каждого репозитория свой: здесь — только служебные папки
  инструментов в корне (`.claude/`, `.vs/`), у сабмодулей — их сборка, данные и
  настройки IDE.

## Пакеты выпуска

```bash
powershell -NoProfile -ExecutionPolicy Bypass -File "D:\\Prog\\Calendar\\build-packages.ps1"
powershell -NoProfile -ExecutionPolicy Bypass -File "D:\\Prog\\Calendar\\build-packages.ps1" -SkipApk
cmd //c "D:\\Prog\\Calendar\\build-packages.bat" -noui      # то же с полным выводом
```

`build-packages.ps1` — основной: этапы с анимацией и итогом, вывод каждого
этапа — в `Build/logs/NN-<этап>.log`, на ошибке — строки `[ОШИБКА]`/`FAIL!`
из журнала и путь к нему. С перенаправленным выводом (так его запускает агент)
анимации нет, по строке на этап. Пароль ключа он проверяет `keytool` до
сборки и отдаёт дочерним процессам только через их окружение; `apksigner`
читает его оттуда же (`env:`), в командных строках пароля нет. Функции
скрипта можно проверить без сборки: `. .\build-packages.ps1` только их
определяет (`Read-Secret` принимает подставные клавиши и буфер обмена).
Файл — UTF-8 **с BOM**: без него PowerShell 5.1 читает кириллицу как ANSI.

Собирает в `Build/` (в `.gitignore`): `Build/Windows` — MSI и setup.exe
планера и сервера с админ-панелью (`build-installer.bat` каждого проекта,
WiX 3 из `%WIX%`),
`Build/Android` — APK, `Build/Linux` — архивы сервера, сайта и службы MCP для Ubuntu
26.04 (`build-linux.ps1`, ниже), `Build/SHA256SUMS.txt`. Исходники пакетов —
в `packaging/` проектов, здесь только порядок их сборки.

- **Linux — `build-linux.ps1`** (его же зовёт `build-packages.ps1`;
  `-SkipLinux` — без него): Docker Engine в WSL-дистрибутиве `Ubuntu-26.04`,
  `packaging/linux/Dockerfile` сервера и бэкенда сайта — сборка, тесты
  (`tst_server`, `tst_bench`, `tst_admin`, `dotnet test`, `node --test`) и образы; затем
  образ сервера запускается и отвечает на `/api/ping` (из Windows —
  `127.0.0.1:8767`, сайт — `8768`), а тесты сайта идут ещё раз против него.
  Код 3 — Docker в WSL нет. Docker из PowerShell —
  `wsl -d Ubuntu-26.04 docker …`; путь `D:\…` там — `/mnt/d/…`. Устройство и
  установка — `PACKAGING.md`, «Linux: Docker в WSL».

- **`-SkipApk`** (`-skipapk` у батника) — всё, кроме APK: без ключа и пароля,
  `Build\Android` не очищается, прежний APK остаётся. Этим режимом агент и
  проверяет скрипт пакетов целиком — пароль ему не нужен.
- **APK подписывается ключом выпуска** `%USERPROFILE%\.android\cosmos-release.jks`
  (`COSMOS_KEYSTORE`), пароль — `COSMOS_KEYSTORE_PASS` или скрытый вопрос
  при запуске. **Агент пароль не вводит и не спрашивает**: собрать пакеты с
  настоящей подписью запускает владелец. Для проверки самих скриптов —
  отладочный ключ: `COSMOS_KEYSTORE="$USERPROFILE\\.android\\debug.keystore"
  COSMOS_KEYSTORE_PASS=android`, и после проверки такой APK из
  `Build/Android` удаляется, чтобы его не приняли за выпуск.
- APK выпуска **не ставится на телефон пользователя**: там отладочная подпись и
  настоящие данные, переход — только по процедуре из `PACKAGING.md`.
- Установщики не запускать на этой машине: MSI ставится в Program Files и
  просит права администратора. Проверять — административной распаковкой
  (`msiexec /a <msi> /qn TARGETDIR=<временная папка>`) и запуском распакованного
  exe без Qt в `PATH` с `--data-dir` во временную папку; окна установщиков —
  снимком (PrintWindow) первой страницы и «Отменой». Таблицы MSI (служба,
  права, порядок действий) читаются через COM `WindowsInstaller.Installer`.
- **Службу сервера на этой машине не ставить и не запускать** — ни
  установщиком, ни `sc create`: это системная настройка, и она за владельцем.
  Код службы проверяет владелец установкой; агент — тем, что `--service` вне
  диспетчера служб отказывается, а всё остальное работает и в консоли.
- **Админ-панель проверяется на тестовом сервере**: `CalendarServerAdmin.exe
  --config <server.ini тестовой папки>` (или `--data-dir`) — без службы, без
  UAC и мимо настоящей базы; `--grab <папка>` снимает все страницы, вкладки
  аккаунта и диалоги в PNG, не показывая окна на экране.

## Правила проверок

- **На телефоне настоящий планер пользователя.** Проверки идут только в
  песочнице: `--data-dir /sdcard/Android/data/org.calendarplanner.app/files/testdb --demo`;
  после проверки песочница удаляется, а планер запускается обычным образом
  (он сам вернёт свой снимок виджетов и план будильников). Подробности — в
  `Calendar/CLAUDE.md` и ниже, «Локальное окружение».
- **Виджеты на рабочем столе телефона — пользователя.** Не добавлять и не менять.
- **Сервер на этом ПК обычно запущен** — это боевой экземпляр с аккаунтами, его
  не останавливают. Для проверок поднимается второй, со своим портом и папкой
  данных (`run-server.bat -p 8766 -d <папка>`).
- **Тяжёлые нагрузочные замеры запускает владелец** (`CalendarServer/tests/bench-all.ps1`,
  `CalendarServerBench tune` с обычными длительностями и подобные — минуты и
  десятки минут с полностью занятым процессором). Агент готовит скрипт и
  команду, а после прогона читает журнал и результаты.
- **Задача в планере заканчивается релизными сборками**: `release/CalendarPlanner.exe`
  и подписанный APK собраны, тесты прошли (`Calendar/CLAUDE.md`, «Релизные
  сборки»). У сервера — его 55 тестов, 18 тестов админ-панели (`tst_admin`)
  и 9 тестов бенчмарка (`tst_bench`).
- **Задача в сайте заканчивается проверкой в браузере**: 64 теста
  `node --test` сайта и 53 теста бэкенда (`dotnet test`, один — с
  `WEB_TEST_SERVER` тестового сервера) прошли, сайт открыт во встроенном
  браузере перед тестовым сервером (`run-server.bat -p 8766 -d <папка>` и
  бэкенд на `127.0.0.1:8780`) на ширине ПК и телефона. Дошла ли правка до
  планера — настоящим планером в песочнице, вход в которую пишет
  `CalendarWeb/tools/planner-sandbox` (`CalendarWeb/CLAUDE.md`, «Проверка в
  браузере»). Бэкенд, как и сервер, — на `127.0.0.1`, наружу не открывать.

- **Задача в MCP**: 17 тестов `CalendarWebMCP` и новые тесты `tst_planner`, а вживую —
  настоящий клиент. Настольный режим — только с `--data-dir` во временную папку (у неё свой
  сокет), облачный — с тестовым сервером и бэкендом на своих портах, с `PublicUrl` на этот
  порт. **Планеры песочницы останавливаются по номеру процесса, а не по имени**: рядом
  может работать настоящий планер пользователя.

(`git clone <бандл> <папка>` разворачивает её целиком).

Пути на этой машине (в других местах будут свои):

| | |
|---|---|
| Qt | `D:\Qt\6.5.3` — киты `mingw_64`, `msvc2019_64`, `android_*`, `wasm_*` |
| Компилятор | `D:\Qt\Tools\mingw1120_64\bin` |
| CMake, Ninja | `D:\Qt\Tools\CMake_64\bin`, `D:\Qt\Tools\Ninja` |
| Android SDK | `D:\Android\SDK` (NDK `25.1.8937393`, platform `android-33`) |

| .NET | SDK 10.0.403 (бэкенд сайта); пакеты тестов — из локального кэша NuGet |

| Docker | Engine 29.1 и buildx 0.30 внутри `Ubuntu-26.04` (`docker.io` из архива Ubuntu), без Docker Desktop |

Данные приложения: `%APPDATA%\CalendarPlanner\CalendarPlanner\` (`planner.db`,
`settings.ini`).

**Сервер на этом ПК.** Служба `CosmosCalendarServer` (с 25.10.2026, версия 1.1
из MSI): `C:\Program Files\CalendarServer\CalendarServer.exe`, LocalService, база,
настройки и журнал — в `%ProgramData%\CalendarPlanner\CalendarServer`, куда без
прав администратора не заглянуть (агенту — тоже: состояние — `Get-Service`,
ответ — `/api/ping`). Порт 8765, адрес в домашней сети `192.168.0.146`
(Ethernet). Управляет ею админ-панель. Прежняя база консольного сервера 1.0,
`%APPDATA%\CalendarPlanner\CalendarServer\server.db`, больше не используется:
служба взяла её копию при установке. Телефон видит его
по Wi-Fi напрямую, брандмауэр пропускает. Если связи нет — `adb reverse tcp:8765
tcp:8765` и адрес `127.0.0.1:8765` на телефоне.

**WSL и Docker.** Дистрибутив `Ubuntu-26.04` с Docker Engine внутри —
только для Linux-сборок (`build-linux.ps1`); его виртуальный диск — на `N:`
(SSD, места много), не на `C:`. Агент работает с ним сам: `docker` — от
пользователя по умолчанию, настройка дистрибутива — `wsl -u root`, без
пароля. В Windows стоят VPN (`happ-xray`, Radmin VPN), и DNS-посредник WSL
на шлюзе молчит, поэтому в `/etc/resolv.conf` дистрибутива прописаны
8.8.8.8 и 8.8.4.4 (`generateResolvConf=false` в `/etc/wsl.conf`). Порт,
опубликованный контейнером, WSL пробрасывает на `127.0.0.1` Windows:
контейнерам — порты от 8766, **не 8765**, где боевая служба.

**Тестовый телефон.** Подключён по USB (`adb devices`), Android 13. Экран
блокировки без пароля: если аппарат спит, `adb shell input keyevent
KEYCODE_WAKEUP` и свайп вверх (`input swipe 360 1300 360 400`) открывают рабочий
стол, дальше приложением можно управлять через `adb shell input tap`. Разрешения
спрашивать не у кого — просить владельца разблокировать не нужно.

Снимок экрана телефона — `adb exec-out screencap -p > файл.png`, и **только
через `cmd`**: PowerShell пропускает вывод через кодировку и дописывает BOM,
после чего PNG не открывается. Окно настольной сборки снимается из PowerShell
через `System.Drawing` (`CopyFromScreen` по прямоугольнику из `GetWindowRect`),
а нажать в нём можно `SetCursorPos` + `mouse_event`: так проверяется то, что
видно только глазами, — рамки, цвета, выравнивание. На **заблокированной**
сессии Windows этого нет: `CopyFromScreen` отвечает «The handle is invalid», и
проверять остаётся на телефоне — `adb` работает и при погашенном экране.

На телефоне лежит **настоящий планер пользователя**. Проверки не должны менять
его данные: файл для импорта готовьте отдельный, со своим `X-WR-CALNAME` (он
создаст новый календарь, который потом удаляется вместе с записями), файлы из
`/sdcard/Download` за собой убирайте. Файл с именем существующего календаря
вольёт записи в него — разобрать их обратно будет нечем. `adb push` в Git Bash
требует `MSYS_NO_PATHCONV=1`, иначе путь `/sdcard/...` превращается в
`C:/Program Files/Git/sdcard/...`, а залитый файл до системного выбора не
доберётся, пока его не проиндексирует media store:
`adb shell content call --uri content://media/external/file --method scan_file
--arg /sdcard/Download/<файл>`.

**Песочница планера по умолчанию смотрит на боевой сервер** — адрес
`192.168.0.146:8765` зашит в планер. Прежде чем входить или регистрироваться
в песочнице (`--data-dir` на телефоне или на ПК), положите в её `settings.ini`
группу `[sync]` с `serverAddress=127.0.0.1:8766` (ключ в `[General]` не
читается) и посмотрите на поле «Адрес сервера» в окне входа; на телефоне ещё
`adb reverse tcp:8766 tcp:8766`. Однажды тестовый аккаунт так попал на боевой
сервер.

Синхронизацию на телефоне проверяйте **тестовым аккаунтом** на сервере с
отдельной папкой данных: на вопрос «Скопировать события и задачи этого
устройства в аккаунт?» отвечайте «Не копировать», а после проверки выходите из
аккаунта — его копия на устройстве удалится, локальный планер останется
нетронутым. `adb shell input text` не печатает кириллицу: названия тестовых
записей — латиницей. Проверочный будильник («Настройки → Будильник → Проверить
будильник») звучит по-настоящему — через канал будильника, даже без звука
звонка.
